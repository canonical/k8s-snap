Autonomous Issue Triage + Fix Bot

A reproduce-first bot that takes a GitHub bug report as far down the triage → reproduce → test → fix pipeline as it safely can, and stops at a human-reviewed draft PR — never merging.

TL;DR — the revised recommendation

Four independent reviewers (security, k8s-snap maintainer, ML-systems skeptic, ops/rollout) converged on the same reshaping of the original plan:

1. Triage first, fix later

The always-on triage bot (dedup, missing-info gate, inspect.sh parse, labels/routing) is the real, cheap ROI. Ship it as a zero-LLM script in week 1. The Fixer is a separate, gated, later funding decision.

2. Wrap, don't build, the fix engine

Copilot coding agent / Claude Code Action already do issue→draft-PR. Our differentiator is the k8s-snap-specific glue: the e2e Harness oracle, the inspect.sh parser, and the cross-repo build wiring.

3. Decouple the reproduction oracle

Don't let the same LLM invent both the test and the pass/fail bar (reward hacking + flaky false-repros). A deterministic probe confirms the symptom in the live cluster before any test is written.

4. Treat all untrusted text as data, never prompt

Tarball logs and adjacent-repo code comments are attacker-controlled. Parse them deterministically; never feed raw strings to the model. Firewall bot PRs from the repo's live auto-merge --admin + backport chain.

Honest expectation: on k8s-snap's real issue mix (networking races, dqlite, multi-node), a net-value-positive Fixer resolve rate is ~14–20%, and infra-bug attempts cost $13–28 each (runner compute, not tokens). The triage bot pays for itself regardless; the Fixer is a bet on a narrow slice.

    • 1 · Goals & the mandated workflow

    The bot must implement this exact flow (from the brief):

    1. First, try to reproduce the issue.
    2. First, create an e2e test that captures it — except for docs updates.
    3. If not reproducible, ask the reporter for specific input (e.g. an inspect.sh inspection report), then stop.
    4. If reproducible, fix it cleanly and minimally. If the fault is in an adjacent repo (k8sd, k8s-snap-api), check it out locally, fix it there, wire it back, make the e2e test pass locally, then open a draft PR in that repo and a draft PR in k8s-snap so CI reproduces it.

    In scope (v1 target)

    • Triage: dedup suggestion, missing-info gate, label + route
    • Reproduce & test-first for tractable issue classes
    • Draft-PR-only fixes; human review always required

    Explicitly out of scope (v1)

    • Auto-merge; security / crypto / auth fixes
    • Large refactors (>3 modules / ~200 lines), feature work
    • Anything a non-maintainer can trigger

    2 · How k8s-snap actually works

    Every design decision is constrained by these mechanics (verified against the repo). The maintainer review corrected several of the original plan's assumptions — shown as corrected.

    Language split & adjacent repos

    Snap = Python e2e + bash wrappers + YAML + snapcraft. The Go core lives in k8sd and k8s-snap-api. build-scripts/components/k8sd/{repository,version} pin the repo & ref; build-component.sh does git clone --depth 1 -b <ref>, applies patches, make dynamic.

    E2E harness

    tox -e integration over a Harness abstraction on LXD containers corrected (not VMs) / Multipass / Juju. Every test must carry a tag (pull_request, …) — enforced at collection time, so a mistagged file aborts the whole run.

    Build cost is the bottleneck corrected

    There is no "swap in a prebuilt binary" path. Any k8sd (Go) fix needs a full snapcraft --use-lxd build (~20–40 min, FIPS Go toolchain, GOEXPERIMENT=opensslcrypto, dqlite .sos). Only k8s/ (python/bash/yaml) & docs fixes skip it.

    CI reproduces draft PRs for free

    e2e-tests.yaml accepts artifact/channel + test-collection-repo/branch. A bot branch's new test runs in CI against the built snap automatically.

    Existing automation to reuse & respect

    ci/security_triage.py (Python + gh + pinned SHAs + least-priv) is the house style. Also live: stale, Jira sync (KU/epic KU-25), backport auto-approve + auto-merge --admin cron danger.

    Reproduction reality corrected

    Multi-node is the norm, not the exception: PR-tagged test_clustering.py/test_dns.py use node_count(2..4). Single-node LXD reproduces roughly the test_smoke.py class only. Networking/dqlite/upgrade bugs need bridges, self-hosted xlarge runners, or specific images.

    Stage A · Triage Bot

    Trigger issues:[opened,edited]. Always-on, Haiku-tier or zero-LLM. No code execution. Delivers value even if the Fixer never ships. This is the first increment.

    Stage B · Fixer Bot

    Trigger: a maintainer applies bot:fix (write-access gate). Agentless-style pipeline (Localize → Probe → Test → Repair → Verify) with a bounded repair loop. Sandboxed; draft-PR-only.

    4 · The reproduction oracle — decoupled

    The single most important correction from review. If one LLM writes both the test and decides what "pass" means, it will reward-hack (sleep past races, weak asserts) and a 2/3 flaky-guard still yields ~22% false-repro on racy cluster tests.

    Deterministic probe → then test

    flowchart TD A[issue symptom
    deterministic parse] --> B[Probe script
    kubectl get · journalctl · k8s status] B --> C{symptom present
    on unpatched HEAD?} C -- "no" --> D[/cannot-reproduce
    ask reporter · STOP/] C -- "yes: signature match" --> E[baseline flake run
    5-7x on HEAD] E --> F{stable red?} F -- "intermittent" --> G[/label flaky
    human review · STOP/] F -- "deterministic red" --> H[generate e2e test
    assert against PROBE output] H --> I[apply fix] I --> J[probe + test GREEN
    N reruns] style D fill:#b23,color:#fff style G fill:#c9a227,color:#111 style J fill:#2a7,color:#fff

    Why this shape

    • Probe is ground truth. A hand-written, per-issue-class diagnostic (not model output) decides whether the symptom exists. The generated test asserts against the probe's signal, so the model can't move its own goalposts.
    • Baseline-flake gate. Measure the failure rate on unpatched HEAD first. Only a stable red qualifies as "reproduced"; intermittent → label flaky, hand to a human.
    • Signature match. The probe must see the same error signature as the report (panic string, event reason), not just any failure.
    • Docs exception. Docs/markdown issues skip the oracle entirely and go straight to a content PR.
    Probe library is the asset we own and grow: one small deterministic checker per tractable issue class (service-not-ready, config-not-applied, wrapper-arg-regression, CRD-missing, …).

    5 · Cross-repo fix flow

    The hard case from the brief: fault is in an adjacent repo. Review made the true cost explicit — a k8sd fix is a 3-repo chain with a mandatory human merge+tag in the middle, and the bot cannot make k8s-snap CI green until a human acts.

    merges+tags API/k8sd. Bot cannot self-unblock. F->>H: request review, list the exact merge order H->>H: merge+tag adjacent, drop replace, approve
    Consequence for v1: only area/k8s-snap (python/bash/yaml/docs) fixes are a clean single-PR loop the bot can drive to green locally. Go/API fixes are staged drafts for a human to sequence — still useful, but not "hands-off". This is why cross-repo is a later increment, not v1.

    Decision: wrap Claude Code Action as the repair driver (self-hostable, our key, Actions-native, scriptable for cross-repo). We build the Localize/Probe/Oracle/Cross-repo glue around it — that's the part no off-the-shelf agent knows.

    6.2 · Pipeline shape — agentless vs agentic

    Agentless / fixed pipeline chosen

    Deterministic stages, bounded cost, interpretable, testable. Best fit for infra where reproducibility matters more than open-ended reasoning.

    Full agentic loop

    More capable on messy tasks, but unbounded cost/latency and hard to audit. Reserved for the repair step only, inside a cost/step cap.

    Prior art we borrow

    Agentless (localize→repair→validate), SWE-agent (ACI), LIBRO/Issue2Test (repro-test generation), Prow (k8s label lifecycle).

    6.3 · Model & sandbox

    Model tiering

    Cheap tier (Haiku-class) for triage/classify; frontier tier (Sonnet-class) only inside the gated repair loop. temperature=0 for fixes. Pin model versions; monthly prompt-regression check.

    Sandbox

    Repair + e2e run in LXD on a self-hosted runner (matches existing e2e substrate; multi-node needs bridges + xlarge). Egress allowlist: api.anthropic.com, api.github.com, snap store, package mirrors. Bot machine account, not a human PAT.

    7 · Security & guardrails

    From the adversarial review. These are architectural requirements, not nice-to-haves — the bot reads attacker-controlled text and can open PRs into a repo with live auto-merge.

    CRIT-1 Tarball / log prompt injection

    Attack: inspect.sh logs contain verbatim attacker strings; embedded fake </system> tags hijack a naive Haiku parse (mechanically = CVE-2025-66032, CVSS 8.7, which the plan cites).

    Mitigation: never feed raw tarball text to the model. Deterministic extraction (grep/parse) pulls typed fields (channel, os, node count, panic signature) into a struct; only that struct — never free text — reaches the LLM. No tool-calls enabled during parse.

    CRIT-2 Second-order injection via repo code

    Attack: the bot reads source (incl. adjacent-repo code it's about to build) whose comments carry instructions.

    Mitigation: localize on AST skeletons with comments stripped; treat all file content as data; the repair step runs with no network except the egress allowlist.

    CRIT-3 Issue-edit race on the bot:fix gate

    Attack: benign issue gets labeled, attacker edits the body to inject a payload; any re-fetch during the run reads the mutated body.

    Mitigation: SHA-pin the issue body at label time; the run only ever uses that snapshot. Any change → abort. Gate strictly on label.actor having write access (verify via API, not payload).

    CRIT-4 Live auto-merge + backport chain

    Attack: the repo already runs an auto-merge --admin cron and backport auto-approve. A bot PR that lands a passing label could ride that path to main and release branches with no human.

    Mitigation: all bot PRs carry bot:generated + no-backport; add these to the auto-merge/backport exclusion lists. Draft PRs can't auto-merge; keep them draft until a human un-drafts. Document as a hard invariant.

    HIGH-1 build-component.sh runs code the bot wrote

    Attack: building an adjacent-repo fix executes pre-patch.sh/build.sh from the branch the bot just authored — arbitrary code exec by construction.

    Mitigation: that's exactly why build+e2e run only in the egress-locked LXD sandbox on an ephemeral runner with a scoped, short-lived token and OUTPUT DROP default. Never on a privileged host.

    Token scope: contents:write + pull_requests:write, issues:read. Never issues:write beyond labels/comments.
    CLA/DCO: bot commits sign-off as k8s-snap-bot@canonical.com; exempt via the existing signed-canonical-cla path.
    Kill switch: a repo-level bot:freeze label + workflow env flag halts all bot runs instantly.

    8 · Cost & reliability — honest numbers

    Cost per attempt corrected up

    ClassDominant cost$/attempt
    docs / markdowntokens only~$0.20
    python/bash/yaml (k8s/)single-node LXD$2–8
    Go (k8sd) / multi-nodefull snap build + xlarge runner$13–28

    The original "~$0.50/fix" assumed a binary-swap that doesn't exist. Runner compute — not tokens — dominates infra bugs.

    Reliability expectation

    • Resolve rate on k8s-snap's real mix: ~14–20% net-positive (SWE-bench numbers don't transfer — cluster bugs are harder than library bugs).
    • Fault-localization across 3 repos is ~40–55% accurate → restrict cross-repo until proven; ~14% wrong-repo risk otherwise.
    • Caps: hard wall-clock 20 min for python-class, separate long-lane for build-class; ≤1–2 repair retries; monthly spend alert; abort+notify on cap.
    • Kill metric (below) decides go/no-go objectively.

    9 · Phased rollout — each phase is a real gate

    Not a checklist to rush — each increment must clear its gate before the next is funded. The kill metric is mean time-to-first-meaningful-human-action on a new issue; baseline it now, before any bot.

    • wk 1–2
      0 · Triage bot (zero-LLM)
      dedup, missing-info gate, tarball parse, label/route. Pure Python + gh. Gate: reduces time-to-first-action >25% with <5% mislabels.
    • mo 1–2
      1 · Fixer shadow — docs + python only
      Wrap Claude Code Action; comment-only (no PR), draft PRs for docs. Gate: shadow diffs judged useful by a maintainer on ≥50 issues.
    • mo 3–4
      2 · Narrow live Fixer
      Real draft PRs for the tractable single-repo classes; probe library + oracle live. Gate: >15% human-accept, <5% regression on a temporal-holdout eval.
    • mo 5–6
      3 · Cross-repo (staged drafts)
      Only if Fixer shows >30% override rate and a positive time-to-action trend. Adds k8sd/api staged draft PRs with human sequencing.
    • ongoing
      4 · Maintain
      Named owner, monthly prompt-regression + shadow re-eval, pinned models, spend review. Bot rot is real; fund it or retire it.

    10 · What the four reviewers changed

    The plan was reviewed by four sub-agents with deliberately different lenses. Each materially reshaped it:

    Security / adversarial

    Flagged: delimiter defense is not real; tarball + repo comments are injection vectors; issue-edit race; live auto-merge/backport chain.

    Changed: deterministic parse + AST skeletons (CRIT-1/2), SHA-pin gate (CRIT-3), auto-merge exclusion invariant (CRIT-4), egress-locked sandbox (HIGH-1).

    k8s-snap maintainer

    Flagged: no binary-swap — k8sd fix = full 20–40 min build; 3-repo human merge+tag chain; test-tag collection trip-wire; LXD containers not VMs; multi-node is normal.

    Changed: build-cost reality (§2, §8), cross-repo staged-draft flow (§5), scope cut to single-repo classes for v1, tag-validation preflight.

    ML-systems skeptic

    Flagged: self-oracle reward-hacking; 2/3 guard → ~22% false-repro; closed-issue eval is data-leakage; diff-overlap ≠ correctness.

    Changed: decoupled probe-first oracle (§4), baseline-flake gate, temporal-holdout eval, two-axis human accept rubric (§8).

    Ops / cost / rollout

    Flagged: two-bot split is right but Fixer isn't "v1"; phases were checkboxes not gates; wrap existing agents; name a kill metric.

    Changed: triage-first funding split, wrap-Claude-Code-Action (§6), gated increments (§9), time-to-first-action kill metric.
